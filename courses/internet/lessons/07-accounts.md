# 7. Accounts and permissions

[Course home](../README.md) · [Curriculum](../CURRICULUM.md)

**Learning goal:** Distinguish signing in from granting access, and choose limited permissions.

An account connects activity to a service identity. Authentication checks a sign-in claim; authorisation determines what that identity can do. Signing in successfully does not mean you should share every file or accept every permission request.

Use a distinct strong password or passphrase for each account; a password manager can help. Enable multi-factor authentication when available and keep recovery methods secure. MFA adds a check but is not a promise that scams or account compromise are impossible. Never give a sign-in or recovery code to someone who asks for it in a message.

A permission request should fit the task. A simple event timetable should prompt questions if it asks for contacts, microphone access or editing access to all your files. Declining a request may limit a feature. Prefer a less intrusive route when it meets the need; do not grant access merely to remove a prompt.

For shared material, viewer access is enough when someone only needs to read. Editor access permits changes and may have wider effects. Review the named people and any general link access. “Anyone with the link” can include people beyond those you intended if the link is forwarded. Exact options differ between services.

## Answer and reasoning

Decline and read the public listing, or investigate the permission's documented purpose before deciding. Never bring real recovery codes into a course exercise. Any real recovery plan should use secure storage controlled by the account owner.

## Use it somewhere else

Make a paper permission checklist: task, requested access, why needed, smaller alternative, and how access could later be removed.
